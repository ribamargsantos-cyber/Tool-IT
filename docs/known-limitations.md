# Limitações conhecidas

Atualizar a cada fase.

| # | Limitação | Impacto | Plano |
|---|---|---|---|
| L1 | Host de desenvolvimento sem MySQL, Redis ou Laragon | Migrations, triggers de auditoria e filas **não foram validados** em MySQL/Redis; testes rodam em SQLite/array | Executar perfil `mysql` da suíte no Laragon (task 013) |
| L2 | SDK .NET 10 (LTS) não instalado (só SDK 9.0.308) | Agent alvo `net8.0` provisório; .NET 8 sai de suporte em 10/11/2026 | Instalar SDK 10 e migrar `TargetFramework` (task 005) |
| L3 | Composer global com `platform.php=8.1` | `create-project`/`require` podem resolver versões antigas | Usar `COMPOSER_HOME` isolado ou `config.platform.php` no projeto |
| L4 | Laragon é stack de desenvolvimento | Menos robusto que serviços dedicados | ADR-013 e task 014 |
| L5 | Captura de tela não cobre tela de bloqueio/UAC/DRM | Operador vê "indisponível" | Documentado (task 010) |
| L6 | Sem teste em ARM64 e Windows 10 antigo | Compatibilidade não comprovada | task 013 |
| L7 | Reverb no Windows não validado sob carga | Tempo real pode exigir ajustes | task 010/013 |
| L8 | **Serviço Windows nunca instalado de verdade**: o ambiente de desenvolvimento não é Administrador. O MSI (`ToolitSetup`) e o script `Install-ToolitAgent.ps1` foram validados só estruturalmente (tabelas do MSI, extração `msiexec /a`, `-DryRun`); `sc create`, início automático atrasado, ações de recuperação e reinício do PC **não foram exercitados** | Pode haver ajuste no script/serviço ao primeiro uso real | Rodar como Administrador numa VM/PC de teste e registrar em `test-evidence.md` (antes do piloto de 5 máquinas) |
| L9 | Coleta medida em **uma** máquina (Windows 11, 12 CPUs, 36 GB) | Custo em PCs modestos, Windows 10 e ARM64 desconhecido | task 013 |
| L10 | Agent usa `winsqlite3.dll` do Windows (Windows 10 1607+) | Windows anterior não suportado | decisão consciente (ADR-014) |
| L11 | A chave privada é protegida por DPAPI **escopo máquina**: qualquer processo local com acesso ao arquivo pode desproteger; a barreira real é a ACL do diretório (aplicada só quando elevado/SYSTEM) | Um administrador local pode copiar a identidade | Documentado no modelo de ameaças (T3); mitigação: revogação individual + alerta de uso por duas origens (task 007) |
| L12 | Agregação horária de métricas e alertas não existem; histórico bruto de 7 dias | Sem tendência de longo prazo | task 007 |
| L13 | Temperatura/sensores não coletados | Campo sempre vazio | decisão consciente (sem fonte confiável) |
| L14 | Periféricos: `WmiMonitorID` só retorna monitores com EDID legível; sob a conta SYSTEM `Win32_Printer` **pode** não listar impressoras instaladas por usuário (hipótese, não verificada — os testes rodaram como usuário comum) | Inventário de impressoras pode ficar incompleto no serviço | Verificar quando o serviço rodar como SYSTEM (L8) |
| L15 | Vulnerabilidades .NET: o scan precisa de `--source https://api.nuget.org/v3/index.json` neste host (fonte corporativa configurada está inacessível) | Scan falha silenciosamente com a configuração padrão | usar a fonte pública no CI |
| L16 | O token de registro viaja pela linha de comando do `AgentToolit.exe` durante a instalação (e como propriedade do MSI) | Administrador local pode vê-lo por instantes; log verboso do MSI o mascara (`MsiHiddenProperties`) | Tokens curtos/uso único; considerar entrega por arquivo protegido (task 012) |
| L17 | O MSI não é assinado; o pacote autossuficiente (≈ 33 MB) não recebe correções do .NET pelo Windows Update | Aviso “editor desconhecido”; correções exigem reempacotar | task 012 (assinatura + atualização assinada do Agent) |
| L18 | O `.vdproj` só compila no Visual Studio/`devenv.com` com a extensão Installer Projects (não com `dotnet build`); `dotnet list package` falha na solução por causa dele (rodar por projeto) | CI precisa de Visual Studio | Avaliar WiX na task 012 se for preciso CI sem VS |
| L19 | `ProductVersion` do MSI é 1.0.0: instalar outro MSI com a mesma versão não dispara atualização | Atualizações exigem aumentar a versão | Automatizar a versão junto de `AgentToolit.csproj` (task 012) |
| L20 | Encerrar sessões de um usuário (desativar, redefinir senha, "encerrar sessões") só derruba sessões com `SESSION_DRIVER=database`; com outro driver o acesso de usuário desativado continua barrado por `EnsureUserIsActive`, mas as sessões de quem segue ativo não são derrubadas | Em Redis/arquivo o botão não encerra sessões | Indexar sessões por usuário se usar Redis (task 011) |
| L21 | Alertas dependem do agendador: `schedule:run` precisa rodar **a cada minuto**; parado, nada abre nem fecha | Alertas atrasados ou ausentes | `docs/deployment/server.md`; monitorar o próprio agendador (task 007) |
| L22 | Alerta de um volume que deixou de existir não fecha sozinho até o endpoint ser removido/desativado | Alerta "preso" | Fechar por inatividade da série (task 007) |
| L23 | Alertas só aparecem na interface; sem e-mail/webhook | Depende de alguém olhar o painel | Notificações externas (futuro, fora do escopo atual) |
| L24 | Telas administrativas revisadas no navegador embutido (desktop ~1000 px e emulação de celular 375 px) com **dados de pré-visualização descartáveis**; não testado em Chrome/Edge/Firefox reais nem em dispositivo físico. URLs de usuário usam o id numérico (`/users/2/edit`), não UUID — acesso protegido por `users.manage` global | Pode haver ajuste visual fino | Revisão em navegadores reais antes do piloto |
| L25 | **A implantação em Docker nunca foi executada** (sem Docker no ambiente de desenvolvimento): `docker build`, `compose up`, o `nginx -t`, o script de init do MySQL, os *healthchecks* e a ordem `migrate → app` não foram exercitados. Também: o usuário da aplicação mantém `UPDATE`/`DELETE` em `audit_logs` (só o *trigger* o protege); `log_bin_trust_function_creators=1` é necessário para criar *triggers* sem SUPER com binlog ligado | Primeiro `up` pode exigir ajustes | Executar em servidor de teste conforme `docs/deployment/docker.md` e registrar em `test-evidence.md`; revogação por tabela na task 014 |
| L26 | Software some do inventário na **primeira** coleta completa sem ele (a task 006 pede 2 coletas); coleta com leitura parcial do Registro, mas marcada como não truncada, gera remoção e reaparecimento falsos no histórico | Ruído no histórico de software | Exigir 2 coletas (contador `missed_count` em `software_items`) ou o Agent sinalizar leitura parcial (task 006) |
| L27 | Histórico de inventário guarda só o **diff** (o payload de cada snapshot não é guardado), limitado a 50 nomes de software e 100 mudanças por coleta; IPs, espaço livre/uso de disco e `boot_time` não contam como mudança; só há histórico a partir da implantação deste recurso (snapshots antigos têm só contagens) | Não dá reconstruir o estado exato de uma data passada | Aceito; guardar snapshots completos só se houver requisito de auditoria de configuração |
| L28 | ~~2 testes de segurança falhavam (`TrustedProxiesTest` e `HeadersTest`)~~ **Resolvido em 2026-10-15**: o `phpunit.xml` não fixava `APP_URL`, então o `manager/.env` local (`https://toolit.rgss.trade`) fazia o cliente de teste enviar requisições HTTPS com o host de produção; agora `APP_URL=http://localhost` é forçado no `phpunit.xml` (suíte: 397 aprovados). Não era defeito de segurança no código | — | — |
| L29 | Tarefas usam poll curto (ADR-021): entrega em até ~10 s após criação/aprovação (medido 2–11 s no E2E com o Manager em disco local; com o Manager lendo o código do compartilhamento de rede `Z:` cada requisição levou 2–37 s) | Sem resposta "instantânea" no painel | Aceito; reduzir `TaskPollSeconds` (mín. 5 s) se necessário |
| L30 | Corrida do claim (dois consumidores, um vencedor) provada só **sequencialmente em SQLite**; o UPDATE condicional não foi exercitado com dois processos concorrentes em MySQL | Duplicação teórica não descartada em produção | Teste de concorrência real em MySQL (task 013) |
| L31 | Só o Admin tem `tasks.approve` e o criador nunca aprova a própria tarefa: com **um único Admin**, tarefas de alto risco criadas por ele ficam pendentes até expirar | Instalação pequena não consegue usar `process.kill`/`agent.restart`/serviço fora da allowlist | Ter ao menos 2 Admins (ou dar `tasks.approve` a outro papel com escopo) |
| L32 | Handlers que **alteram** o sistema foram validados só com *fakes* e com processo descartável (`ping.exe`) criado pelo teste; `service.start/stop/restart` em serviço real do Windows **não validado** (sessão sem Administrador: no E2E um `service.stop Spooler` chegou ao Agent e falhou com "Acesso negado", o serviço continuou rodando) | Comportamento real do `ServiceController` como SYSTEM (dependentes, timeouts) desconhecido | VM com o serviço instalado (L8) e um serviço descartável criado pelo teste |
| L33 | Allowlist e serviços protegidos só em `config('toolit.tasks')`/`system_settings` (`tasks.service_allowlist`, `tasks.service_protected`), **sem tela de edição**; a lista de protegidos do Agent é fixa no código e não acompanha mudanças no Manager | Mudar política exige editar banco/config; listas podem divergir | Tela em `settings.manage` (task 011) e envio da política ao Agent |
| L34 | Proteção de antivírus no Agent depende do `root\SecurityCenter2` (inexistente no Windows Server): lá só vale a lista fixa (Defender incluído) | AV de terceiros em servidor pode ser encerrado por `process.kill` aprovado | Lista adicional configurável (task 013) |
| L35 | Janela de reutilização de PID entre a checagem do nome e o `Kill` (handles separados); handler abandonado após timeout pode continuar rodando; cancelamento é reportado mesmo que o efeito já tenha começado | Raro, mas possível encerrar o processo errado ou relatar "cancelado" após efeito parcial | Abrir o processo uma vez e matar pelo mesmo handle (task 013) Proposta: ADR-025 (aguarda board). |
| L36 | `agent.restart` envia o resultado e encerra o host com código 75 contando com as ações de recuperação do SCM; que o `WindowsServiceLifetime` propague o `Environment.ExitCode` é **suposição**, não testada (serviço nunca instalado, L8) | O Agent pode simplesmente parar e não voltar | Validar em VM com o serviço instalado |
| L37 | Resposta de `GET /tasks/next` perdida (o Agent desistiu por timeout de 30 s enquanto o servidor ainda fazia o claim) deixa a tarefa `running` sem executor até a lease vencer **e** `tasks:expire` rodar: tipo não idempotente vira `failed` (`lease_expired`), idempotente volta para a fila. Observado no E2E (`process.kill` aprovado, nunca executado, `failed` após 135 s com `tasks:expire` manual) | Tarefa aprovada perdida; depende do agendador (L21) | Aceito (nunca executa duas vezes); considerar confirmação do claim pelo Agent |
| L38 | Aba Tarefas revisada no navegador com Tailwind CDN como aproximação: `npm run build` falha no compartilhamento `Z:` (módulo nativo do rollup, `ERR_DLOPEN_FAILED`); navegadores reais não testados | Classes novas podem faltar no CSS compilado | Rodar `npm run build` em disco local e revisar de novo |
| L39 | Neste ambiente `dotnet test` não roda direto no compartilhamento `Z:` (testhost.exe: acesso negado) — os testes do Agent rodam de uma cópia local de `bin/` + `tests/contracts`; executáveis publicados idem; Pint não grava em `Z:` (usar `--test` e corrigir à mão) | Fluxo de desenvolvimento mais lento | Clonar o repositório em disco local |
| L40 | Sem retenção para `remote_tasks`/`remote_task_attempts` (saídas de até 16 KiB por attempt) e sem notificação externa de aprovação pendente | Crescimento do banco; aprovação depende de alguém abrir `/tasks/approvals` | Job de retenção (task 014); notificações fora do escopo atual |
| L41 | O Agent nunca envia `progress` (a lease fixa de timeout + 30 s basta para os tipos atuais); cancelamento de tarefa **em execução** depende do próximo heartbeat (60 s) e não foi exercitado no E2E (as tarefas reais terminaram em < 1 s) | Cancelar algo longo pode levar até ~60 s | Testar com tarefa longa quando houver (ex.: `inventory.refresh` em PC lento) |
| L42 | `file.send`/`file.fetch` são de risco **médio** sem aprovação por segunda pessoa (decisão do dono, ADR-022; a recomendação era envio = alto) | Um operador com `files.transfer_send` grava sozinho qualquer arquivo de extensão permitida nas pastas da política | Manter políticas estreitas (pastas dedicadas, poucas extensões); reavaliar aprovação para envio |
| L43 | **Não validados:** o executável do serviço transferindo de verdade (no E2E o `AgentToolit.exe` publicado, sem elevação, excluiu as raízes temporárias e recusou tudo — só os handlers rodaram, em processo de teste); `TransferAcl.ApplyRestricted`/`RestrictParent` nunca rodaram elevados (se falharem, as raízes sob `%ProgramData%\Toolit` são excluídas = transferências desligadas); compartilhamentos UNC reais (sempre recusados neste ciclo); interferência de antivírus no `.part`/rename | Comportamento como SYSTEM desconhecido | Rodar o E2E com o serviço instalado numa VM como Administrador (L8) |
| L44 | TOCTOU residual no Agent: o registro de raízes não compara o caminho final do handle da raiz com o configurado (`%ProgramData%\Toolit` pré-criado por outro usuário); o rename usa `FILE_RENAME_INFO` com caminho completo e a pasta de destino fixada por handle (a variante `RootDirectory` devolveu `ERROR_INVALID_PARAMETER` 87 aqui; `NtSetInformationFile` com `RootDirectory` não implementado) | Janela teórica de corrida com quem já pode gravar na pasta-mãe | task 013 Proposta: ADR-025 (aguarda board). |
| L45 | O operador **digita** o caminho da recuperação (sem navegação remota) | Erros de digitação viram `failed` ("não existe") | Navegação remota fica fora do escopo |
| L46 | Disco do Manager: só há checagem de espaço livre (2× o tamanho) na criação do envio; sem quota nem monitoramento; blobs de transferências encerradas ficam 7 dias; apagar um endpoint apaga as linhas em cascata, mas os blobs só saem pelo `transfers:prune` que percorre linhas (podem sobrar órfãos em `storage/app/private/transfers`) | Disco pode encher com transferências grandes ou endpoints removidos | Monitorar o volume (task 014); limpeza de órfãos |
| L47 | Remover um grupo apaga a política dele em cascata, sem `transfer_policy.deleted` na auditoria e sem bloquear a remoção | Mudança de política invisível na trilha | Auditar/bloquear na remoção do grupo Proposta: ADR-024 (aguarda board). |
| L48 | PHP (ICU do `intl`) e .NET (ICU do Windows) podem ter versões Unicode diferentes para NFC/NFKC | Um nome aceito de um lado e recusado do outro | O vetor compartilhado detecta a deriva; rodar os dois testes ao atualizar PHP/.NET/Windows |
| L49 | **Achado do E2E (2026-10-16):** queda do Manager/rede no meio de uma transferência faz o Agent reportar `failed` (o handler guarda o `.part` esperando nova tentativa), mas o Manager trata `failed` como final: a tarefa não é repetida, a transferência vira `failed` e o `.toolit-{id}.part` fica órfão na pasta de destino. Só há retomada quando a tentativa some sem resultado (Agent morto → lease vence → `tasks:expire` recoloca) | Um soluço de rede obriga a refazer o envio do zero e deixa lixo no Inbox | Correção de projeto (não feita aqui): falha transitória → não reportar/recolocar na fila, ou o Manager reabrir `file.*` idempotente; limpar `.part` órfão Proposta: ADR-023 (aguarda board). |
| L50 | Aba **Arquivos**: CSS só conferido de forma aproximada (`public/build` antigo; `npm run build` falha em `Z:`, L38); o JS de DOM não tem teste automatizado (só a lógica pura + `fetch` simulado no Node, 18/18); várias ações da tela não foram exercitadas em navegador real — no E2E o "navegador" foi um cliente HTTP com cookies + CSRF | Problema visual/de interação pode passar | Revisar em navegador real após `npm run build` em disco local |
